1. Introducción al Proyecto

TRAVEL CC es una aplicación móvil diseñada para el transporte pesado de carga. Resuelve un problema crítico: los mapas convencionales (como Google Maps o Waze) están diseñados para vehículos livianos e ignoran restricciones físicas (altura, peso, ancho) y normativas (permisos de vialidad desde 4,2 m).

Nuestra propuesta de valor se basa en 3 pilares:

  1. Navegación Heavy: Rutas calculadas según las dimensiones reales del vehículo.
  2. Fleet Tracking: Monitoreo en tiempo real para jefes de flota.
  3. Mapa que Aprende (Crowdsourcing): Los conductores reportan desvíos y anomalías, mejorando la base de datos geoespacial colectivamente (validado con datos de CONASET: 2.934 colisiones con camiones en 2024).

Este documento presenta el desarrollo del módulo Frontend de la aplicación, construido con Flutter y siguiendo el patrón MVVM. Se detallan las decisiones técnicas, la arquitectura implementada y los conceptos aprendidos durante el desarrollo.

3. ¿Qué es Flutter y por qué lo usamos?

Flutter es un framework de UI de código abierto creado por Google. Permite compilar aplicaciones nativas para móviles (Android), web y escritorio desde una única base de código escrita en el lenguaje Dart.

¿Por qué lo elegimos para TRAVEL CC?

  • Multiplataforma real: Un solo desarrollo para conductores que usan Android y jefes de flota que usan Web.
  • Rendimiento nativo: Compila a código máquina, logrando 60 FPS, crucial para una app de navegación en movimiento.
  • UI consistente: Permite replicar exactamente el diseño oscuro y de alto contraste definido en nuestro proyecto.
  • Hot Reload: Acelera el desarrollo al ver cambios en tiempo real sin reiniciar la app.

4. Conceptos Fundamentales de Dart

Dart es el lenguaje detrás de Flutter. Conceptos clave que aplicamos en TRAVEL CC:

4.1. Tipado estático con inferencia

El tipo se declara o se infiere, evitando errores en tiempo de ejecución:

final String truckId = 'TRK-023';  // Tipo explícito
final speed = 85.5;                // Tipo inferido (double)

4.2. Null Safety

Dart obliga a manejar valores nulos explícitamente, evitando el temido "NullPointerException":

String? driverName;  // Puede ser null
String name = driverName ?? 'Desconocido';  // Valor por defecto

4.3. Asincronía (Future/async/await)

Fundamental para simular llamadas a red (como el login):

Future<void> onLogin() async {
  _isLoading = true;
  notifyListeners();
  await Future.delayed(const Duration(milliseconds: 1500));
  _isLoading = false;
  notifyListeners();
}

4.4. Clases y ChangeNotifier

Usamos clases que extienden ChangeNotifier para los ViewModels, que gestionan el estado de la pantalla y notifican a la View cuando algo cambia.

5. Arquitectura del Proyecto (MVVM + Clean Architecture)

Aplicamos una combinación de Clean Architecture y el patrón MVVM (Model-View-ViewModel) para garantizar que el código sea escalable, testeable y mantenible.

El Patrón MVVM en TRAVEL CC:

  • Model: Estructura de los datos puros (ej. datos simulados de camiones activos).
  • View: La interfaz de usuario (UI). Lo que se ve. Solo contiene Widgets.
  • ViewModel: El "cerebro". Conecta Model y View. Maneja el estado y la lógica.
La View nunca debe contener lógica de negocio compleja. Solo "escucha" al ViewModel y se reconstruye cuando este avisa que algo cambió.

Flujo de datos:

┌─────────────┐     ┌──────────────┐     ┌─────────────┐
│    View     │────▶│  ViewModel   │────▶│    View     │
│  (Widget)   │     │(ChangeNotifier)│   │  (Rebuild)  │
└─────────────┘     └──────────────┘     └─────────────┘
       ▲                    │
       │                    ▼
       └───────────── notifyListeners()

7. Anatomía de un Widget en Flutter

En Flutter, todo es un Widget. Son como piezas de LEGO que se combinan para formar la UI.

7.1. Tipos de Widgets

  • StatelessWidget: No cambia con el tiempo (ej. un texto estático, un ícono).
  • StatefulWidget: Puede cambiar. En MVVM, delegamos este estado al ViewModel para mantener la View lo más simple posible.

7.2. Widgets de Layout más usados en TRAVEL CC

WidgetUso en el proyecto
ScaffoldEstructura base de cada pantalla (appBar, body, floatingActionButton)
Column / RowOrganizan elementos vertical u horizontalmente
StackApila elementos uno sobre otro (usado en el mapa para superponer UI)
ContainerCajas para dar espacio, color o bordes
ExpandedOcupa el espacio disponible en un Row/Column
SingleChildScrollViewPermite scroll cuando el contenido excede la pantalla

8. Análisis Archivo por Archivo

8.1. main.dart — El director

Es el punto de entrada de la app. Inicializa la aplicación, aplica el tema oscuro y conecta el sistema de navegación:

void main() {
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  @override
  Widget build(BuildContext context) {
    return MaterialApp.router(
      title: 'TRAVEL CC',
      theme: AppTheme.darkTheme,
      routerConfig: appRouter,
    );
  }
}

8.2. app_colors.dart — La paleta centralizada

Centraliza todos los colores. Si el cliente pide cambiar el naranja por azul, solo modificamos esta línea y toda la app se actualiza:

class AppColors {
  static const Color actionOrange = Color(0xFFFF6B00);
  static const Color warningYellow = Color(0xFFFFB800);
  static const Color criticalRed = Color(0xFFE53935);
  static const Color backgroundDark = Color(0xFF121212);
  // ... más colores
}

8.3. auth_viewmodel.dart — La lógica del login

Contiene la lógica del login. Usa controladores para leer los inputs y simula una carga asíncrona:

class AuthViewModel extends ChangeNotifier {
  final TextEditingController idController = TextEditingController();
  String _selectedRole = 'usuario';
  
  void selectRole(String role) {
    _selectedRole = role;
    notifyListeners();  // Avisa a la View que cambió el rol
  }
}

8.4. fleet_view.dart — La lista de camiones

Muestra las estadísticas de la flota. Utiliza un Consumer para reconstruir solo la parte de la UI que depende de los datos:

body: Consumer<FleetViewModel>(
  builder: (context, viewModel, child) {
    return ListView.builder(
      itemCount: viewModel.trucks.length,
      itemBuilder: (context, index) {
        final truck = viewModel.trucks[index];
        return _buildTruckCard(context, truck);
      },
    );
  },
)

9. Sistema de Navegación con GoRouter

Usamos el paquete go_router para una navegación declarativa y segura. Permite deep linking y manejo de rutas con parámetros.

Configuración principal:

final GoRouter appRouter = GoRouter(
  initialLocation: '/login',
  routes: [
    GoRoute(path: '/login', name: 'login', builder: ...),
    GoRoute(path: '/map', name: 'map', builder: ...),
    GoRoute(path: '/fleet', name: 'fleet', builder: ...),
    // ... 16 rutas más
  ],
);

Diferencia clave aprendida:

  • context.goNamed('login'): Reemplaza la pantalla actual. Ideal para flujos lineales (Inicio → Login) donde no queremos que el botón "Atrás" regrese al inicio.
  • context.pushNamed('detalle'): Apila la pantalla. Permite volver atrás con context.pop().

10. Integración del Mapa con flutter_map

Para el mapa utilizamos flutter_map (basado en OpenStreetMap) en lugar de Google Maps, porque:

  • No requiere API Key de pago.
  • Es open source y gratuito para uso comercial.
  • Permite personalización total de marcadores y capas.

Dependencias agregadas en pubspec.yaml:

dependencies:
  flutter_map: ^7.0.2
  latlong2: ^0.9.0  # Para manejar coordenadas LatLng

Lección aprendida:

Al integrar el mapa en web/tablet, el contenedor debe envolverse en Positioned.fill para obligarlo a ocupar todo el fondo. Sin esto, el mapa puede renderizarse con tamaño 0x0 en algunos navegadores.

11. Principios de Diseño Aplicados

11.1. DRY (Don't Repeat Yourself)

No escribimos colores o espaciados al azar. Usamos variables centralizadas en app_colors.dart y app_spacing.dart. Ejemplo:

// ❌ MAL: colores repetidos
Container(color: Color(0xFFFF6B00))
Container(color: Color(0xFFFF6B00))

// ✅ BIEN: variable centralizada
Container(color: AppColors.actionOrange)
Container(color: AppColors.actionOrange)

11.2. Single Responsibility (SOLID)

Cada clase tiene una única responsabilidad:

  • FleetView solo dibuja la UI.
  • FleetViewModel solo piensa (maneja datos y lógica).

Si hay un bug visual, sabemos que está en la View. Si hay un bug de datos, está en el ViewModel.

11.3. Separation of Concerns

La lógica de negocio está aislada de la UI. Esto permite:

  • Probar la lógica sin necesidad de renderizar la UI.
  • Cambiar el diseño sin tocar la lógica.
  • Reutilizar ViewModels en diferentes Views.

12. Glosario de Términos Técnicos

Widget
Unidad básica de construcción de UI en Flutter. Todo en Flutter es un Widget.
ChangeNotifier
Clase de Flutter que avisa a la View cuando sus datos internos cambian, mediante notifyListeners().
Consumer
Widget que "escucha" a un ChangeNotifier y reconstruye su hijo cuando hay cambios.
StatelessWidget / StatefulWidget
Widgets que no cambian / Widgets que pueden cambiar de estado.
GoRouter
Paquete de Flutter para navegación declarativa, con soporte para deep linking.
Provider
Paquete de gestión de estado que facilita el uso de ChangeNotifier en la UI.
Hot Reload (r en terminal)
Recarga rápida que aplica cambios de UI sin perder el estado de la app.
Hot Restart (R en terminal)
Reinicia la app desde cero aplicando todos los cambios de código.
Mock Data
Datos simulados usados en el desarrollo hasta que el Backend esté listo.
Crowdsourcing
Obtención de información de manera distribuida entre los usuarios (conductores).
MVVM
Model-View-ViewModel. Patrón arquitectónico que separa la UI de la lógica de negocio.
flutter_map
Paquete de Flutter para renderizar mapas de OpenStreetMap sin API Key.
